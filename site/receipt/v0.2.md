# Receipt specification, v0.2

This page is what `https://agent-custody.dev/receipt/v0.2` resolves to: the `predicateType` carried by every receipt. It describes the signed objects a verifier meets, field by field, and the checks a verifier must make. The formats are standard on purpose, so a verifier in any language needs nothing from this codebase.

## Building blocks

| | |
| --- | --- |
| Envelope | [DSSE](https://github.com/secure-systems-lab/dsse). `{ payloadType, payload (base64), signatures: [{ keyid, sig (base64) }] }`. The signature is Ed25519 over the pre-authentication encoding `"DSSEv1 " + len(payloadType) + " " + payloadType + " " + len(payload) + " " + payload`. |
| Statement | [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md), serialised as canonical JSON: keys sorted, no whitespace, `undefined` dropped. |
| keyid | Hex SHA-256 of the SPKI DER encoding of the Ed25519 public key. Signatures are matched to trusted keys by keyid. |
| Digest | Hex SHA-256 of the canonical JSON of a value. |
| Log | [RFC 6962](https://www.rfc-editor.org/rfc/rfc6962) hashing: `0x00 || leaf` for leaves, `0x01 || left || right` for nodes. Leaves are the canonical JSON of the receipt envelope. Inclusion proofs and consistency proofs follow [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162) sections 2.1.3 and 2.1.4. The empty tree's root is the SHA-256 of nothing. |

## Provenance

Every field that describes the call carries a provenance label. This is the part a reader must not skip.

| label | meaning |
| --- | --- |
| `attested` | signed by a key other than the issuer's, today the principal's delegation key |
| `observed` | obtained by the issuer itself, outside the agent's control; only a gateway can produce this |
| `claimed` | originates from the agent, the model, or the agent's own process, with no independent check |

## The receipt bundle

A receipt on disk, `receipts/<receiptId>.json`, is a bundle of three parts.

```json
{ "envelope": <DSSE over the receipt statement, signed by the issuer>,
  "treeHead": <DSSE over a TreeHead, signed by the issuer or by the log>,
  "inclusion": { "leafIndex": 0, "treeSize": 1, "hashes": [] } }
```

### The receipt statement

`payloadType` is `application/vnd.in-toto+json`. The statement is:

```json
{ "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "tool-call:<tool>:<receiptId>", "digest": { "sha256": "<digest of request.args>" } }],
  "predicateType": "https://agent-custody.dev/receipt/v0.2",
  "predicate": { ... } }
```

### The tree head

`payloadType` is `application/vnd.agent-custody.treehead+json`. The payload is `{ treeSize, rootHash, timestamp, log? }`, where `log` names the log that signed it when the server runs more than one; a verifier told which log to expect checks it. It is signed by the issuer's key when the issuer keeps the log itself, or by the log's key when the issuer appends to a log run by someone else. Which key signed it is what a verifier reports: a tree head signed by a party that is not the operator says the receipt was in a log the operator could not rewrite.

### The upstream attestation

An upstream that holds a key may sign what it returned. It puts a DSSE envelope on its result's `_meta["agent-custody/upstream-signature"]` with `payloadType` `application/vnd.agent-custody.upstream+json` and payload `{ receiptId, tool, contentDigest }`, where `contentDigest` is the digest of `{ content, isError }` of the result, the part the agent receives, and `receiptId` is the id the gateway passed to the upstream in the call's `_meta`. The gateway embeds the envelope as `execution.upstream`. A verifier given the upstream's key checks the signature, the receipt id, the tool, and the digest, and then reports the execution as attested by that key rather than merely observed by the gateway.

#### Provider-native deliveries

Where the upstream is a wrapper around a provider that signs with a shared secret, `execution.upstream` may instead be `{ provider: "stripe-webhook" | "github-delivery", rawBody, signature, bind, deliveryId? }`: the delivery exactly as received, its signature header, and a dot path into the body whose value must appear in the receipt's result. A verifier given the secret recomputes the HMAC (Stripe: over `<t>.<rawBody>` with the timestamp within tolerance of the receipt's; GitHub: over the raw body) and checks the binding. The report labels the execution `attested (shared secret)`, weaker than a key-based attestation, since the secret is shared.

### Financial outcomes and reconciliation

`operation` and `reconciliation` are optional additions to v0.2; earlier receipts retain their meaning. A financial call always carries a committed authorization before forwarding. Its first receipt is financially pending or unknown even when API execution is `executed`. A known non-forwarded call can be financially failed beside `withheld` or `denied`. A retry of an existing operation has its own receipt: `execution.status: "withheld"`, and `operation.originalReceiptId` differs from `receiptId` and names the first receipt. A reconciliation receipt uses `execution.status: "executed"` for the successful provider read and `operation.status: "confirmed"` or `"failed"` for the payment outcome. A consumer must not read it as a policy-allowed call of the tool: no policy ran, and its `policy.reasons` say so.

The reconciliation preserves the original operation id, idempotency key, budget, principal, agent, tool and grant. Its signed `lookup` must hash to the original `lookupDigest`. Its provider JSON must report a mapped terminal state and the same idempotency key at `identityPath`, and the original bundle must verify and precede it in the log. This records the gateway's observed read; independent provider signatures are not implied. Withheld provider results verify as committed until restored. [Financial operations](../../packages/receipts/docs/financial-operations.md) describes reservation and recovery semantics.

### The authorization statement

For a tool the gateway treats as consequential, and for every door arrival that can change something at the origin (any method but GET, HEAD, and OPTIONS, or a route in the door's `precommit`), the producer signs and logs this before forwarding the call. `payloadType` is `application/vnd.in-toto+json`; the statement has the same `subject` as the receipt will and `predicateType` `https://agent-custody.dev/authorization/v0.1`. The predicate is the receipt's `receiptId`, `timestamp`, `issuer`, `principal`, `agent`, `delegation`, `tool`, `request`, `facts`, `consumed`, `approval` when required, `policy`, and optional submitted `operation` evidence, and nothing about the execution outcome, because there is none yet. The producer writes it as `receipts/<receiptId>.authorization.json` and embeds it in the receipt as `authorization`, with the inclusion proof and tree head of its own leaf. If the log refuses it, the call is not forwarded and the receipt's execution is `withheld`. An authorization verified on its own, after a crash left no receipt, must come from a gateway or a door; a gateway's must name a submitted operation, a door has none.

### The human approval

Added optionally after v0.2 shipped. `payloadType` is `application/vnd.agent-custody.approval+json`. Its canonical JSON payload is:

```json
{
  "version": "0.1",
  "approvalId": "<UUID>",
  "principal": "user_456",
  "agent": "support-agent",
  "tool": "stripe.refund",
  "argsDigest": "<sha256 of the complete arguments>",
  "amount": 2500,
  "currency": "GBP",
  "beneficiary": "cust_123",
  "issuedAt": "2026-10-18T12:00:00.000Z",
  "expiresAt": "2026-10-18T12:05:00.000Z"
}
```

`amount`, `currency`, and `beneficiary` are optional, copied when present from the call's arguments by their names or the receipt's configured `approval.fields` mapping. Amount is a safe integer in minor units; currency and beneficiary are nonempty strings. The digest covers all arguments, including extra fields. The approval id is single use at the gateway, and the validity window is `[issuedAt, expiresAt)`, with expiry strictly after issuance. One or two distinct trusted keyids must sign the same payload; repeating a signature counts once. Human approval keys are trusted independently of receipt issuer and principal keys. Two keys representing two different people is an operational assumption.

The gateway checks before facts/policy and again immediately before forwarding, then atomically consumes the id in a shared persistent directory. Its receipt records the check, signer ids, and consumption time. Failure before facts denies; expiry or a replay race during awaited work withholds. A consumed id remains burned after a crash or unknown outcome. A verifier cannot establish global single use from one receipt alone.

When a receipt includes a precommit, `authorization carries this approval` compares the envelope, signature threshold, and field mapping with the final receipt. `authorization approval was valid` requires the precommit's own approved status, distinct trusted signer observations, and a check inside the signed validity window. Final check times, consumption time, and a late refusal may differ from the precommit.

The envelope carries the action fields and an unsalted digest of the complete arguments. Under a private capture rule the receipt withholds the envelope at `approval.envelope` as one salted commitment, and the precommit carries the same commitment; `reason` is withheld too. The status, `requiredApprovers`, `checkedAt`, `consumedAt`, `approverKeyids`, `fields`, and `provenance` stay in clear and a capture note may not name them. A verifier that restores the envelope and the arguments, with the capture key or a disclosure, runs the signature, window, and binding checks. Without them, it passes those checks as committed. When the issuer withholds nothing under `request.args`, an approved envelope stays in clear, unless the tool name is masked, and a verifier fails `approval signatures (human keys)` for a forwarded call whose note withholds the envelope but nothing under `request.args`. `checkedAt` and `consumedAt` are ISO 8601 times with an offset (`Z` or `+HH:MM`); a time without an offset is a structural fault, because `Date.parse` reads it as local time. The gateway refuses an approval whose lifetime (`expiresAt` minus `issuedAt`) exceeds `approvals.maxLifetimeSeconds`; the receipt does not carry that setting.

### The key document and checkpoints

A log publishes `GET /.well-known/agent-custody-log.json`: `{ log?, keys: [{ keyid, alg: "ed25519", publicKeyPem, validFrom, validTo? }] }`, current key first, retired keys after it, so a verifier fetches keys from the log's own origin and pins them by keyid. A log also publishes checkpoints, signed tree heads at increasing sizes, as files `<tenant>/<treeSize>.json` on a host of their own and at `GET /checkpoints?since=<size>`; each is `{ treeSize, rootHash, signedAt, treeHead }` with `treeHead` the same signed envelope as in a receipt. Any two checkpoints, or a receipt's head and a later checkpoint, are compared with a consistency proof. A witness countersigns a checkpoint by adding its own signature to the same envelope, DSSE allowing several; a witness publishes `/.well-known/agent-custody-witness.json` in the same shape as the log's key document, and a verifier that requires the witness checks the newer head for a signature by one of those keys.

### The delegation grant

`payloadType` is `application/vnd.agent-custody.delegation+json`. The payload is `{ version: "0.1", principal, agent, scopes[], issuedAt, expiresAt }`, signed by the principal. The gateway refuses to start outside the validity window and embeds the grant in every receipt, so a verifier re-checks it rather than trusting that the gateway did.

## Verification

A verifier holds public keys only: issuer keys, principal keys, human approval keys for approval-bearing forwarded calls, and log keys when a remote log is used. It needs no access to the issuer, the agent, or the upstream system. The checks, in order:

1. `receipt signature (issuer key)`: the envelope verifies against a trusted issuer key.
2. `receipt payload type`: the envelope's `payloadType` and the statement's `predicateType` are the values above.
3. `structural parts in clear`: the capture note, if present, is well formed (a mode and paths as segment arrays) and names no structural part, and the parts every check reads (ids, the tool, the grant, an attested principal's key id, the status, the decision and the policy digest, an authorization's tree head and proof, the digests) are present and of the right type; nothing else is decided if this fails. Then `issuer kind is known` and `issuer keyid matches signer`.
4. On a gateway receipt: `gateway receipt carries a delegation` and `gateway receipt carries a policy decision`. On a door receipt: `door receipt carries a policy decision`. On an egress receipt: `egress receipt carries a policy decision`, `egress destination observed` (the tool name is observed and equals the host and port of the observed `destination` fact), `egress relayed only for a checked agent` (an executed, failed, or errored connection names an agent with provenance `observed`), `egress open committed before relaying` (such a connection carries an authorization), and `egress peer matches the destination` (for an IP literal, `execution.result.peer` is that address; for a host name, it is not a loopback, private, shared, link-local, metadata, multicast, or reserved address, nor an IPv4-mapped or NAT64 address that carries one).
5. With a delegation: `delegation signature (principal key)`, `delegation binds principal and agent` (the grant's principal and agent equal the receipt's, and the signing key is the receipt's attested principal keyid), `delegation valid at receipt time`, and `executed tool within delegated scope` (an executed or failed call names a tool in the grant's scopes). Without one: `principal is claimed, not attested`.
6. When an approval record is present on a forwarded call: `approval signatures (human keys)` requires its threshold of distinct trusted approver signatures; `approval payload binding` checks principal, agent, tool, full arguments and mapped action fields; `approval valid at forward time` checks the recorded check and consumption times against the validity window; `approval consistent with execution` requires an approved, consumed record with matching signer observations. Withheld arguments and a withheld envelope pass as committed until they are disclosed or decrypted. These approval checks run on forwarded calls only: a denied or withheld call verifies as an authentic refusal, with no approval key, whether its approval was valid or not.
7. `request args digest`: the digest of `request.args` equals `request.argsDigest` and the subject digest; on an executed or failed call, `execution result digest`: the digest of `execution.result` equals `execution.resultDigest`. When the `capture` note names paths under the part, the digest is over the full value and a salt derived from the salts of those values (sha256 over their concatenation, in note order); a verifier given neither the values with their salts nor the key that reveals them passes the check as committed, the detail says so, and the subject digest is still checked; given them, the digest is recomputed from the restored values, and a value that contradicts its commitment fails the check. A named path that holds no commitment fails it. Each captured fact gets `fact <name> value` and `fact <name> args` under the same rules, and every other named path a `withheld <path>` line.
8. With an upstream signature and an upstream key: `upstream signature (upstream key)`, the envelope verifies against a trusted upstream key and binds to this receipt id, this tool, and this result's content digest. With a provider delivery and the provider's secret: `upstream signature (provider secret)`, the HMAC verifies, Stripe's timestamp is within tolerance, and the bound value appears in the result. When the result or the delivery body is withheld and a key or secret was given, `upstream signature not checked` passes with a note instead.
9. With a policy: `policy decision consistent with execution` (allow never pairs with denied; an enforced deny always does; a deny with `enforced: false` may sit beside an executed, failed, or errored call, and the check names the mode) and `no policy errors on an allow`.
10. `tree head signature` against log keys then issuer keys, reporting which signed; `tree head matches inclusion proof size`; `log inclusion proof` recomputes the root from the leaf hash of the canonical envelope and the proof.
11. Optionally, with a copy of the log, `log file root matches tree head` recomputes the root at the tree head's size.

A bundle passes only if every check passes. The report then lists each field with its provenance, so the reader knows what was proven and what was merely claimed.

## Auditing across receipts

Given two signed tree heads and a consistency proof between their sizes, `older is not larger than newer` and `newer log extends older log` establish that nothing before the older head was rewritten. A log serves the proof at `GET /consistency?old=M&new=N` and its current signed head at `GET /head`.

## The log API

A log reached over HTTP implements four routes. `POST /append` with `{ leaf }` returns `{ inclusion, treeHead }`, the tree head signed by the log's key, and may require a bearer token. `GET /root?size=N` returns `{ treeSize, rootHash }`. `GET /consistency?old=M&new=N` returns `{ oldSize, newSize, hashes }`. `GET /head` returns `{ treeHead }`.

## Reference implementation

[`@agent-custody/receipts`](/receipts/) on npm implements every object and check on this page. Verification is the pure function `verifyBundle`; auditing is `auditExtends`. The [conformance vectors](/receipt/vectors) are generated by its test suite, and a second implementation agrees with the reference when it reproduces every verdict in them; the [browser verifier](/verify) on this site does, and so does the Python verifier in `agent_custody.verify`, written from this page.
